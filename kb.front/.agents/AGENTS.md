# DIOS Knowledge Web — инструкции для AI-агентов

Этот документ задаёт правила разработки frontend приложения **DIOS Knowledge**. Перед изменениями учитывайте продуктовые сценарии базы знаний и контракты backend. Цель — быстрый, предсказуемый интерфейс работы со знаниями без лишних архитектурных прослоек.

## 1. Назначение продукта

DIOS Knowledge — корпоративная база знаний, в которой сотрудники создают и публикуют статьи, организуют навигацию по пространствам и коллекциям, находят достоверную информацию и используют её при решении заявок в DIOS ITSM. Через Knowledge MCP те же опубликованные знания доступны AI-ассистентам **только в пределах прав вызывающего пользователя**.

Ключевые сценарии UI:

- Поиск по базе знаний, переход к релевантному разделу статьи, отображение источников.
- Навигация: `Space → Collection → Collection / Article`.
- Создание статьи, Markdown-редактирование, предпросмотр, сохранение новой редакции.
- Публикация, снятие с публикации, история редакций, восстановление редакции.
- Настройка доступа к Space, Collection и Article, если у пользователя есть соответствующие полномочия.
- Импорт документов в Markdown, ссылки на Media Service, экспорт опубликованного/разрешённого содержимого.
- Связи статей с другими знаниями и с задачами ITSM — через явные интеграционные контракты, а не локальную бизнес-логику ITSM.

## 2. Технологический стек

- **React 19+**, **TypeScript**, **Vite**.
- **SCSS Modules** для локальных стилей; общие токены и глобальные стили — в `shared/styles`.
- Markdown — **канонический формат содержимого статьи**. Редактор и renderer должны сохранять совместимость с серверным Markdown.
- Markdown parser / renderer, syntax highlighting и библиотеку редактирования выбирайте исходя из требований конкретного экрана. Не подключайте инструменты для streaming Markdown только потому, что они используются в DIOS AI Chats: обычное чтение статьи не является потоковой генерацией.
- Используйте существующий UI kit и общие компоненты экосистемы DIOS, если они подходят. Не создавайте параллельный набор базовых контролов.

Не добавляйте новую библиотеку состояния, маршрутизации или Markdown без обоснования её роли и проверки совместимости с проектом.

## 3. Архитектура: FSD-based

Разделяем приложение **по владению состоянием и пользовательским сценариям**, а не механически по визуальным компонентам.

```text
src/
├── app/
├── pages/
├── widgets/
├── features/
├── entities/
└── shared/
```

Зоны ответственности:

| Слой | Ответственность |
| --- | --- |
| `app` | Router, providers, bootstrap, глобальные стили, wiring приложения. Без предметной бизнес-логики. |
| `pages` | Композиция конкретных страниц, загрузка параметров маршрута, screen-level состояния. |
| `widgets` | Самостоятельные блоки интерфейса: навигация Knowledge, просмотр статьи, редактор, search panel. |
| `features` | Пользовательские действия с предметным смыслом: публикация, сохранение редакции, перемещение элемента, выдача доступа. |
| `entities` | Модели, типы, stores, read-only UI и операции над бизнес-сущностями. |
| `shared` | BackendCaller, транспорт, базовый UI kit, hooks, утилиты, настройки, общие стили. Без знаний о `Article`, `Collection` и других предметных сущностях. |

Правила импортов:

- Зависимости направлены **вниз по FSD**: `app → pages → widgets → features → entities → shared`. Допустимо пропускать уровни, например `pages → entities`.
- Один slice не импортирует внутренности другого slice того же слоя. Публичные экспорты — через `index.ts`, когда они действительно нужны потребителям.
- **Внутри одного slice используйте относительные импорты**. Между слоями — настроенные алиасы (`@entities/...`, `@shared/...`).
- Не создавайте slice на каждый файл или кнопку. Фича нужна, когда действие имеет отдельную ответственность и/или состояние.
- Если виджет требует общий store, определите, **какой entity/feature владеет состоянием**, а не поднимайте всё в `app`.

Пример структуры — ориентир, а не обязательные пустые каталоги:

│   ├── create-article/

## 4. Состояние и взаимодействие с backend

**Не создавайте отдельный API-слой только потому, что есть HTTP-запрос.** Используйте общий `BackendCaller` из `shared/api`, а операции вызывайте из store/feature, владеющего состоянием.

```text
React UI
   ↓
widgets / features
   ↓
entity / feature stores
   ↓
shared/api/BackendCaller
   ↓
Knowledge REST API
```

Создавайте отдельный API adapter/функцию, когда это оправдано: сложный endpoint, несколько запросов, повторное использование, преобразование DTO, особые transport semantics или важное предметное имя.

- `BackendCaller` централизует base URL, заголовки авторизации, обработку ошибок, abort/cancellation и transport.
- В stores остаётся **предметное состояние**: текущая статья, дерево навигации, редакция, сохранение, публикация, поисковая выдача.
- Не превращайте store в универсальный объект, отвечающий одновременно за статьи, поиск, настройки и авторизацию.
- Не дублируйте server state без причины. Согласованно инвалидируйте/перезагружайте данные после mutations.
- Не выводите роли или permissions из UI-констант. Источник истины — backend и его effective permissions.
- Не импортируйте `BackendCaller` напрямую в чистые UI-компоненты: запросом управляет store или action.

## 5. Модель Knowledge в интерфейсе

### Space / Collection / CollectionPlacement

- `Space` — область знаний и верхний контекст доступа.
- `Collection` — контейнер навигации с именем и описанием.
- `CollectionPlacement` — размещение `Collection` или `Article` в конкретной коллекции, включая порядок (`rank`).
- Одна статья может находиться в **нескольких коллекциях**. Не храните единственный `collectionId` как свойство `Article`.
- Дерево коллекций — **навигация, а не дерево наследования ACL для статей**.
- Порядок, перемещение, ограничения циклов и уникальность родителя проверяет backend. UI может подсвечивать недопустимые действия заранее, но не заменяет серверную валидацию.

### Article / ArticleRevision

- `Article` хранит идентичность, slug, `currentRevisionId`, `publishedRevisionId`, статус и метаданные.
- `ArticleRevision` — неизменяемая редакция с Markdown, заголовком, summary и номером.
- Сохранение редактора создаёт **новую Revision**, а не обновляет существующую.
- Публикация — отдельное действие с `revisionId` для защиты от публикации устаревшего состояния.
- При наличии неопубликованных изменений читатель видит **published Revision**, редактор — **current Revision**.
- Restore старой Revision создаёт новую редакцию, а не переписывает историю.
- Backend может завершить публикацию раньше, чем Qdrant закончит индексацию. Не объявляйте индекс актуальным только по успеху `publish`.

Для конфликта редакций (`409`) показывайте понятное сообщение и предлагайте безопасно перечитать актуальную редакцию; не затирайте несохранённый текст автоматически.

## 6. Markdown, медиа и импорт

- Единственный канонический формат статьи — **Markdown**. У редактора должен быть стабильный round-trip между редактированием и сохранением; если используется WYSIWYG, проверяйте потери таблиц, code blocks, изображений и ссылок.
- Render Markdown безопасно. Не допускайте выполнение произвольного HTML/JavaScript, небезопасных `href`/`src` и XSS через пользовательский контент.
- В Markdown хранятся **стабильные ссылки на объекты Media Service**, а не временные signed URLs. Разрешение ссылок выполняется через доверенный backend/Media Service с учётом авторизации.
- Поддерживайте заголовки и стабильные anchors, таблицы, списки, ссылки, изображения, fenced code blocks, копирование фрагментов.
- **Импорт DOCX/PDF и других форматов в Markdown выполняется на backend**. Frontend отвечает за upload, отслеживание статуса, preview и подтверждение/редактирование результата.
- Экспорт в PDF/DOCX — отдельная backend-операция с доступом только к разрешённой редакции.
- OCR, embeddings и индексация Qdrant не выполняются в браузере.

## 7. Доступ и безопасность

- FastAPI/Knowledge backend — **единственный источник истины** для ACL и доступности опубликованной редакции.
- UI может скрывать/отключать операции по effective permissions (`READ`, `WRITE`, `PUBLISH`, `ARCHIVE`), но **не считается security boundary**.
- UI настройки доступа работает с grants (`Subject`, `Resource`, `Permission`) и показывает, какие разрешения прямые, а какие действуют через Space/другие разрешённые ресурсы.
- Не вычисляйте итоговые ACL из нескольких frontend stores и не доверяйте спискам ролей, присланным произвольным клиентским кодом.
- Нельзя отображать текст, заголовки, сниппеты или медиа недоступной статьи, даже если они ранее были в кеше.
- При смене аккаунта/организации очищайте пользовательские кэши и состояние редактора/поиска.
- Избегайте прямых запросов в Qdrant и вызовов поисковых моделей из frontend. Поиск идёт через Knowledge API, который выполняет ACL prefilter и повторную проверку результатов.

## 8. Поиск и навигация по результатам

- Единый Search API поддерживает web UI и Knowledge MCP; frontend **не реализует RAG**.
- Интерфейс использует только авторизованную выдачу backend, а не запрашивает глобальный Top-K с последующей клиентской фильтрацией.
- Результат содержит понятный источник: статья, путь заголовков, фрагмент, при необходимости ссылки на изображение/медиа.
- Реализуйте debounce, отмену устаревшего запроса и корректные состояния `loading / empty / error`.
- Группируйте совпадения одной статьи, если backend возвращает несколько chunks. Не дублируйте статью десятки раз в выдаче.
- По возможности сохраняйте поисковый запрос и фильтры в URL, чтобы ссылкой на поиск можно было поделиться.
- Не показывайте технические scores, raw embeddings, Qdrant IDs и внутренние details индексации обычному пользователю.

## 9. UX и стиль

- Разделяйте три явных режима: **чтение опубликованной статьи**, **редактирование черновика**, **история/сравнение редакций**.
- Не скрывайте факт наличия неопубликованных изменений от редактора. Статус `Draft / Published / Archived` должен определяться backend-моделью, а не локальным угадыванием.
- Сохранение, публикация, удаление/архивирование и управление доступом должны иметь понятные состояния операции и обработку ошибок.
- Для долгих операций (импорт документов) предоставляйте прогресс/статус и возможность вернуться к результату.
- Поддерживайте клавиатурную навигацию, читаемые focus states, контрастность и адаптивный layout.
- Не создавайте новые дизайн-токены и варианты базовых компонентов без необходимости. Визуальные правила находятся в `docs/design/ui-guidelines.md`.

## 10. TypeScript и код-стайл

- Строгая типизация; не использовать `any` без явного обоснования.
- Понятные имена по предметной области: `ArticleRevision`, `CollectionPlacement`, `publishArticle`, `saveRevision`, `canPublish`.
- Компоненты должны оставаться преимущественно презентационными; асинхронные операции и состояние — рядом с владельцем сценария.
- Не создавайте классы/абстракции там, где хватает простой функции или существующего store.
- Не дублируйте backend business rules на frontend. Проверки клиента служат удобству, сервер проверяет инварианты.
- Сохраняйте единый стиль файлов, импортов и именования существующего проекта; не переписывайте соседний код без причины.

## 11. Тестирование

Для изменений в ключевых сценариях нужны тесты:

- Просмотр опубликованной редакции не раскрывает текущий черновик.
- `save revision` и `publish` корректно обрабатывают ошибки/`409 Conflict` и не теряют текст редактора.
- Перемещение CollectionPlacement обновляет дерево и откатывает optimistic UI при ошибке.
- Доступ и кнопки учитывают effective permissions, но всегда полагаются на серверную авторизацию.
- Поиск отменяет устаревшие запросы, показывает пустой результат и ведёт на нужный раздел статьи.
- Markdown renderer безопасно обрабатывает пользовательский контент, media references, таблицы, код и ссылки.
- Импорт документов показывает результат преобразования до публикации.

Для независимых компонентов используйте component tests, для stores/features — unit tests с подменой `BackendCaller`, для основных пользовательских потоков — интеграционные/E2E тесты. Не добавляйте тестовую инфраструктуру, дублирующую уже принятую в проекте.

## 12. Чек-лист перед завершением задачи

1. У изменения есть очевидный владелец состояния и корректный FSD-слой.
2. Нет лишней API-прослойки, универсального service или ненужного store.
3. Контракт backend соблюдён; не перепутаны current и published Revision.
4. Проверены права, состояния ошибок, отсутствие утечек недоступного содержимого.
5. Новые элементы доступны с клавиатуры и согласованы с дизайн-токенами.
6. Пройдены существующие проверки TypeScript, lint и релевантные тесты.
7. Новые важные решения документированы; существующая архитектура не усложнена без причины.

**Принцип:** расширяйте DIOS Knowledge через небольшие, явно ответственные slices. Хороший frontend помогает пользователю найти, проверить, сохранить и применить знание, а не повторяет backend-логику или инфраструктуру поиска.
