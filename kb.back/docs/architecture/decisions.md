# Ключевые архитектурные решения

Краткий реестр решений, принятых при реализации. Целевая архитектура — [`.agents/architecture.md`](../../.agents/architecture.md), поиск — [`search.md`](search.md).

## 1. Доступ задаётся только grants; у Space нет `visibility`

Поле `Space.visibility` дублировало ACL (две конкурирующие правды о видимости). «Доступно всей организации» выражается grant `subject=organization, READ`; при создании Space это делает флаг `organizationWide`.

- Space создаёт только администратор (роль IAM `admin`); создатель получает `READ|WRITE|PUBLISH|ARCHIVE` на Space.
- Админ **не обходит ACL**: он управляет grants (`/api/admin/v1/access/grants`), в том числе может выдать их себе.
- Grant выдаётся только на существующий ресурс своей организации; пара ресурс/субъект уникальна (повтор — `409`).

## 2. `AuthType` — тип субъекта, а не роль

`AuthType = USER | SERVICE`; администратор — это роль (`AuthUser.is_admin`). Раньше `ADMIN` был отдельным типом, и админ получал `403` на пользовательском API. Legacy: пока нет сервисных аккаунтов, service-to-service принимает админа.

## 3. `organization_id` денормализован в Collection

Как и в Article: проверка tenant не требует JOIN к Space, ресурс проверяется одинаково во всех модулях.

## 4. Порядок элементов коллекции — дробная индексация

`rank_between(before, after)` (base62, `domain/collections/ranking.py`) вставляет элемент между соседями без перенумерации. Колонка `rank` — `COLLATE "C"`: в языковых collation порядок base62 ломается.

Все изменения дерева одного Space сериализуются `pg_advisory_xact_lock`: это закрывает гонки рангов и циклов коллекций (две параллельные перестановки «A в B» и «B в A»). Уникальные индексы БД — последний рубеж: один родитель у коллекции, без дублей размещений.

Коллекцию с содержимым архивировать нельзя (`409`): сначала элементы переносятся или убираются.

## 5. События — только там, где есть потребитель, через outbox

Доменные события есть только у публикации статьи (`ArticlePublished/Unpublished/Archived`) — их потребляет индексация. Use case пишет их в `outbox_messages` в той же транзакции (`application/outbox.py`); `EventDispatcher` DDF (commit-then-publish) для этого не используется. Payload — полное JSON-представление события, поэтому `event_id` сохраняется при доставке.

Relay (`python -m src.infra.outbox.relay`) просыпается по `LISTEN/NOTIFY`, с опросом по таймауту как страховкой, и ставит Taskiq-задачи. Несколько экземпляров безопасны (`SKIP LOCKED`).

## 6. Статья ↔ редакция: отложенные FK

`articles.current_revision_id/published_revision_id → article_revisions` и `article_revisions.article_id → articles` — циклическая ссылка, поэтому FK объявлены `DEFERRABLE INITIALLY DEFERRED` (проверка при commit).

Архивирование снимает публикацию; восстановленная из архива статья становится черновиком — повторная публикация остаётся явным действием.

## 7. Медиа в Markdown: `media://<attachment_id>`

Каноническая ссылка на вложение Media Service — `![подпись](media://<uuid>)`; frontend сам превращает её в URL. Вложения неизменяемы по id (новая загрузка — новый id), поэтому кеш OCR ключуется `media_id + версия экстрактора` и не требует скачивания файла.

**Ограничения Media Service (вне этого репозитория):**

- `owner_type` не допускает статьи базы знаний — для загрузки «от статьи» нужен новый тип владельца;
- soft-delete вложения ломает неизменяемость опубликованной редакции.

## 8. PostgreSQL 18 и UUIDv7

DDF задаёт `server_default uuid_generate_v7()`. Первая миграция создаёт эту функцию как обёртку над встроенной в PG18 `uuidv7()`; расширения не нужны.
