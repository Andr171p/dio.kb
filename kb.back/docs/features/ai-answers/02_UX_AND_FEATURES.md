# DIOS AI Answers — UX-концепция, сценарии и roadmap

**Статус:** UX/Product Spec, дизайн и контракты требуют прототипирования.  
**Дата:** 21 ноября 2026 г.

## 1. UX-цель

Пользователь должен быстро понять: **что известно, что делать дальше, какие документы это подтверждают и где остаётся неопределённость**.

AI Answers — часть общего поиска DIOS KB, а не копия окна AI Chats. Визуально он должен выглядеть как *обоснованный результат поиска*, а не новый диалоговый интерфейс.

## 2. Продуктовые принципы

1. **Search-first:** обычные результаты появляются независимо от LLM.
2. **Answer-on-demand:** в MVP генерация начинается по явному запросу, чтобы не тратить inference на поиск названия статьи.
3. **Evidence-first:** доступ к подтверждающим фрагментам из ответа — в один клик.
4. **Progressive disclosure:** короткая суть, дополнительные шаги и детали раскрываются при необходимости.
5. **No false precision:** не изображать уверенность несуществующими процентами.
6. **Consistent navigation:** ссылка ведёт на действующую опубликованную статью, по возможности в нужный раздел.
7. **Human control:** пользователь принимает решение о применении действий, эксперт утверждает новые инструкции.
8. **Graceful fallback:** ошибка AI не ломает обычный поиск.

## 3. User journey A — поиск и AI-ответ

### A1. Search overlay в header

При нажатии на лупу разворачивается поисковое поле (референс — характер взаимодействия Atlassian).

**Пока пользователь печатает:**

- показываем title suggestions из PostgreSQL (`prefix` / FTS / `pg_trgm`);
- показываем пространство или раздел результата;
- не вызываем LLM на каждом вводе;
- debounce и отмена устаревших autocomplete-запросов;
- `Enter` открывает страницу обычной поисковой выдачи;
- отдельное действие «Получить AI-ответ» запускает Answers.

Если запрос явно вопросительный, можно выделить действие AI Answers, но не запускать без согласия в MVP.

```text
┌──────────────────────────────────────────────────────────┐
│  🔎  Как устранить ошибку HTTP 401 в 1С?           Enter │
├──────────────────────────────────────────────────────────┤
│  ПОИСК В ДОКУМЕНТАЦИИ                                  │
│  ▸ Настройка HTTP-сервисов 1С       Интеграции           │
│  ▸ Диагностика авторизации IIS      База решений         │
├──────────────────────────────────────────────────────────┤
│  ✧ Получить AI-ответ по вопросу                          │
└──────────────────────────────────────────────────────────┘
```

### A2. Страница результатов

**Desktop layout:** основной контент (AI-ответ и результаты поиска) + панель источников справа.

```text

│ Возможно несколько причин; ... [1]   │     Интеграции · Раздел «Доступ»   │
│                                       │                                     │
│ Что проверить                         │ [2] Диагностика IIS                │
│ 1. ... [1]                            │     База решений · «Авторизация»    │
```

> Все заголовки и рекомендации в макетах условны; интерфейс не должен превращать иллюстративные проверки в гарантированное решение ошибки.

### A3. Клик по citation

Клик по `[1]` открывает **панель подтверждающего источника** (popover/drawer, в зависимости от платформы):

- заголовок, пространство, статус доступности;
- конкретный текстовый фрагмент, используемый в ответе;
- путь заголовков и ссылка-якорь;
- данные публикации/верификации, если они реально существуют;
- «Открыть статью» и «Показать рядом»;
- при изменении ACL — безопасный отказ, без сохранённой копии недоступного текста.

**Критическое UX-правило:** ссылки должны подтверждать ближайшее утверждение, а не просто совпадать по теме.

### A4. Чтение обычных результатов

Под ответом остаётся привычный список результатов со сниппетами и навигацией. Пользователь не обязан доверять генерации.

Полезная доработка: визуально отмечать статьи, действительно использованные для ответа, не скрывая остальные релевантные материалы.

## 4. User journey B — диагностический ответ

Ответ формируется **в зависимости от намерения**, а не всегда по одному шаблону.

| Тип вопроса | Предпочтительный вид |
|---|---|
| «Что такое ...?» | Короткое определение, контекст, 1–2 источника |
| «Как настроить ...?» | Предпосылки, шаги, проверка результата, источники |
| «Почему ошибка ...?» | Возможные причины и диагностические развилки; указать недостающие условия |
| «Сравни X и Y» | Таблица различий, условия выбора, источники |
| «Где находится ...?» | Прямая ссылка на документ вместо длинной генерации |
| «Какая политика действует?» | Точная ссылка на актуальную утверждённую политику; без домыслов |

### Рекомендуемая структура troubleshooting

1. **Краткий вывод:** что подтверждено найденными источниками.
2. **Условия применимости:** версия, окружение, роль, ограничения, если известны.
3. **Проверки / действия:** нумерованные шаги с локальными цитатами.
4. **Как понять, что проблема решена.**
5. **Что уточнить / когда передать эксперту**, если контекста недостаточно.

Не выдавать гипотезу за установленную причину инцидента.

## 5. States UX

| State | Отображение | Действие пользователя |
|---|---|---|
| `idle` | Обычные результаты + CTA AI Answers | Запустить ответ |
| `retrieving` | Результаты доступны, индикатор поиска доказательств | Читать обычные статьи |
| `generating` | Появилась подготовленная панель источников, затем ответ | Продолжить поиск / отменить |
| `answered` | Ответ, цитаты, источники, feedback | Применить, открыть, оценить |
| `insufficient_evidence` | Нет подтверждённого решения; показать близкие статьи | Уточнить запрос / сообщить о пробеле |
| `conflicting_evidence` | Показать несовместимые рекомендации и условия | Уточнить конфигурацию / передать эксперту |
| `error` | Ненавязчивое сообщение о сбое генерации | Повторить; обычный поиск остаётся доступен |
| `access_changed` | Источник перестал быть доступным | Перезагрузить поиск; не показывать старый excerpt |

**Важно:** `insufficient_evidence` и `conflicting_evidence` не следует целиком доверять необоснованному самодиагнозу LLM. Серверу нужен явный контракт, а системам оценки качества — отдельная разметка.

## 6. UX недостаточного ответа

```text
┌─────────────────────────────────────────────────────┐
│ ℹ Не удалось подтвердить решение                    │
│                                                     │
│ В доступных документах недостаточно информации о   │
│ вашей конфигурации. Близкие статьи показаны ниже.   │
│                                                     │
│ [Уточнить вопрос]   [Сообщить о пробеле в знаниях] │
└─────────────────────────────────────────────────────┘
```

Не задавать «Уточнить вопрос» в виде бесконечного чата. В MVP это может открывать короткое поле уточнения и запускать новый одноразовый ответ. Продолжительный диалог — в DIOS AI Chats.

## 7. Feedback

После ответа: иконки полезности и необязательный выбор причины:

- неполный ответ;
- нет решения для моей конфигурации;
- устаревшая инструкция;
- неверные/неподходящие источники;
- противоречащие рекомендации;
- ошибка в процедуре;
- другое.

Не требовать большой формы после каждого ответа. После отрицательной оценки можно предложить **один конкретный следующий шаг**, например «Сообщить об отсутствии инструкции».

Feedback — сигнал для анализа, а не автоматическое доказательство того, что статья плохая.

## 8. Mobile UX

- Один столбец: AI-ответ → «Использовано N источников» → найденные статьи.
- Источники открываются в bottom sheet / drawer.
- Действия копирования и открытия источника доступны без точного попадания в крошечные маркеры.
- Длинные ответы имеют содержательное начало и сворачиваемые детали.
- Состояния loading/error не блокируют навигацию по результатам.

## 9. Доступность и производительность интерфейса

- Полная keyboard navigation: Tab, Esc, Enter, перемещение по suggestions, доступ к citations.
- Правильная роль combobox/listbox для autocomplete; видимый focus state.
- Динамический ответ не должен резко сдвигать уже прочитанные результаты.
- Источники и ссылки — настоящие доступные элементы управления.
- Использовать `aria-live` дозированно: не объявлять весь поток токенов по одному символу.
- При генерации поддерживать отмену и не передавать ответы в навигационную историю автоматически.
- Не блокировать UI на LLM. Для MVP допустим обычный POST + понятное ожидание; в следующей итерации — SSE.
- Не раскрывать текст недоступной статьи в клиентском кеше, истории браузера и аналитике.

## 10. Сценарии интеграции с экосистемой

### Из DIO Desk (следующий этап)

Кнопка «Найти решение» рядом с заявкой. Контекст, переданный в KB с явным набором разрешений: текст ошибки, тип системы, версия, окружение, уже выполненные проверки. AI Answers формирует диагностический ответ, не меняя саму заявку.

### Из AI Chats

Кнопка «Продолжить в AI Chats» для сложного кейса. Передаётся вопрос и ссылки на источники, а не безусловный доступ к старым фрагментам. AI Chats заново проверяет права через KB MCP.

### Для владельцев знаний

Раздел «Возможности улучшения»: повторяющиеся безответные вопросы, плохая находимость, конфликтующие статьи; переход к guided AI-соавтору (см. `04`).

## 12. Критерии приёмки MVP

- Пользователь может получить обычные результаты, даже если генерация не удалась.
- Все показанные источники актуально доступны пользователю.
- Каждая citation указывает на реальный сохранённый источник; неизвестные citations не рендерятся.
- Отсутствие доказательств не превращается в уверенную инструкцию.
- Нельзя вставить в query `organization_id` и получить сведения другой организации.
- Есть latency/cost telemetry без неконтролируемого сохранения исходных корпоративных вопросов.
- Feedback позволяет отличить недостаток знаний от недостоверного или неудобного ответа.

## 13. Что протестировать с реальными пользователями

1. Находят ли участники действие «AI-ответ» в раскрытом поиске?
2. Могут ли они быстро проверить источник для конкретного шага?
3. Что предпочтительнее: summary сверху, step-by-step или переключение типов ответа?
4. Понимают ли они отличие «информация отсутствует» от «модель не нашла»?
5. Насколько понятен переход «не помогло» → «сообщить о пробеле»?
6. Применяют ли они неподтверждённые рекомендации без прочтения условий?

## 14. Вывод

Лучшая первая версия AI Answers для DIOS — **поиск с проверяемым ответом и доступными первоисточниками**, без попытки имитировать полноценный чат. Развитие функций захвата знаний должно происходить как продолжение сценария решения задачи, а не как отдельная сложная административная система.
